# Docusaurus plan audit and discovery record

Date: October 4, 2026. Scope: one bounded pre-implementation audit of the execution
plan, with two independently tasked reviews and a primary review of delivery and
cross-component dependencies. This is a planning assessment, not release approval.

The audited plan had SHA-256
`0a9208ed34a0749cad80dee1855feb9c1dfe0699717eb57f65b330657d01800c`.
The repository base was `ca35845fab8072d48c7a8ef39a125dca97b79366`, with the previously
implemented, uncommitted Docusaurus 3.10.2 upgrade. The
[execution plan](DOCUSAURUS_EXECUTION_PLAN.md) now incorporates the dispositions
below. Existing migration notes and implementation files were not changed by this
audit.

## Assessment

The original plan covered the main framework features and most migration risks.
Its remaining weakness was proving the migration method and the meaning of its
outputs before scaling work. The corrected plan adds an early replay comparison,
an independent content reference, explicit downloadable-data contracts, and earlier
consumer discovery. It also makes the contributor and deployment journeys explicit.

Do not infer that the old branch should be discarded or that regeneration is
already cheaper. The next implementation should establish a reproducible control
and run a bounded pilot; broad content migration follows the selected mechanism.
No additional framework feature, hosting vendor, search service, or backend is
required by this audit.

## Accepted findings and dispositions

### A1 — High: validate the production-content synchronization mechanism

**Observed:** the converter skips existing destinations
([source](scripts/migrate-devdocs.mjs#L532)). The cached production AppNexus page
contains newer deprecation/Microsoft migration guidance, while the converted page
still carries older content. The previous plan required reconciliation but did
not require replay evidence showing how updated sources reach converted outputs.

**Why existing controls were insufficient:** safely repeating a conversion with
unchanged input is different from applying a second upstream snapshot and
preserving migration-only repairs.

**Disposition:** D8 and M2 now require a bounded comparison of in-place
reconciliation versus regeneration into staging with explicit reviewed overrides.
Retain reusable framework/components either way. Use two pinned source snapshots,
shared-include changes, additions/renames/deletions, and a migration-only repair;
compare semantic results, conflicts, and review effort before selecting a method.
Independent runtime/CI work can proceed while discovery continues.

### A2 — High: generated downloads need payload validation

**Observed:** [static/bidder-data.csv](static/bidder-data.csv) contains frontmatter
and Liquid. The existing `build/bidder-data.csv` is byte-identical: 2,865 bytes,
80 Liquid tags, SHA-256
`9a9ac142c2422fa08665e6af8a059840e9601df70bb24fbd5d3904baa133d1ce`.
The [introduction](docs/content/intro.mdx#L111) links `/dev-docs/bidder-data.csv`,
which is absent from the inspected build. Correcting the URL alone would expose
the unrendered template.

**Why existing controls were insufficient:** page/asset presence and HTTP success
do not establish a valid CSV. The previously planned custom JavaScript download
journey did not explicitly cover this separate data export.

**Disposition:** M0 inventories non-HTML generated outputs. M3a validates the CSV's
public path, schema, nonempty records, independently expected values, escaping,
absence of unrendered template material, and add/change/delete freshness.

### A3 — Medium: define an independent semantic reference

**Observed:** the old [example layout](_layouts/example.html#L29) adds contextual
bullets and production-use warnings. Likewise, bidder layouts generate information
not contained in the Markdown body. Current Docusaurus output is already known
to omit some of that content; using it as the fidelity oracle would bless those
omissions.

**Why existing controls were insufficient:** a converter, its normalizer, and
expected data generated by the same implementation can agree on an incorrect
result. The old plan specified preservation without fixing the expectation source.

**Disposition:** M0 now distinguishes a Docusaurus regression baseline from a
legacy-content fidelity reference. Verified ledger entries identify pinned
sources and template/include dependencies plus independently reviewed semantic
expectations. M1/M2 include a control that removes required content while leaving
the page build and route valid. A second full Jekyll implementation is not required.

### A4 — Medium: resolve field meanings before enforcing the schema

**Observed:** the legacy [metadata template](_includes/dev-docs/bidder-meta-data.html#L33)
uses an unknown state for omitted USP/COPPA fields, while the
[contributor guide](docs/dev-docs/prebidjs/bidder-adaptor.md#L1302) describes false
defaults and [BidderFeatures](src/components/BidderFeatures/index.tsx#L46) implements
false defaults. Legacy `no-display` and GPP fallback rules also carry meaning
beyond converting comma-separated strings to arrays.

**Why existing controls were insufficient:** mentioning unknown-versus-false does
not resolve conflicting authorities. Neither TypeScript props nor current
rendering establishes the intended business meaning by itself.

**Disposition:** M2 includes a small field-policy table and maintainer resolution
of conflicts, covering raw forms, missing/false/unknown semantics, provenance,
canonical values, and each consumer. Start with observed fields and projections;
avoid a general-purpose metadata platform. This is a decision requirement, not a
claim that every legacy default or current React default is wrong.

### A5 — Medium: discover download consumers before shared metadata design

**Observed:** the [download template](download.md#L73) depends on filename and alias
overrides, eligibility, recommendations, and version constraints. Its
[JavaScript](assets/js/download.js#L109) also produces a saved configuration file.
The prior D5 dependency allowed discovering these requirements at M6, after M2/M3
had defined a shared metadata contract that already included download selection.

**Disposition:** move read-only contract discovery and representative consumer
fixtures to M0/M2, before M3a acceptance. Keep UI implementation and live service
integration at M6. Alias/filename, unavailable/minimum-version, and saved-config
cases must fit without information loss or a late schema redesign.

### A6 — Medium: accept the contributor journey, not just rendered pages

**Observed:** the [adapter contribution guide](docs/dev-docs/prebidjs/bidder-adaptor.md#L1291)
still points to old paths and navigation metadata; its release process ties
documentation merging to actual adapter release. Agent instructions also contain
an outdated blanket instruction to strip a field still used for bidder discovery.

**Disposition:** M3b updates guides/templates/applicable agent instructions with
the contract change and exercises a synthetic new adapter through documented
authoring, validation, preview, detail/index/CSV outputs, and correct release-based
download eligibility. This requires no real adapter release or external message.

## Delivery and implementation refinements

* **Hosted URLs are an early dependency.** D2/D3/D6 now precede route-affecting
  contracts. Test `.html`, slash, fragment, query, asset/download, and refresh
  behavior on the selected host. Docusaurus documents host-specific differences;
  local client navigation is insufficient. If the CLI deployment path is chosen,
  this organization repository requires an explicit deployment branch.
* **Promote the validated artifact.** M7 now requires a checksummed candidate built
  from reviewed source, validated as a package, and deployed without an implicit
  rebuild. A differently configured preview is a separate artifact. This tightens
  the prior exact-artifact requirement rather than claiming an existing deployment
  workflow is unsafe; no Docusaurus production workflow has been implemented yet.
* **Separate PR and release authority.** M1 explicitly treats PR MDX/plugins as
  executable untrusted code and isolates their cache/artifact writes from trusted
  release work. M7 narrows deploy permissions and ties it to successful trusted
  build/validation. The existing notification job checks out the base context;
  this audit did not establish execution of PR-head code in that job.
* **Bound cutover drift.** M5/M7 record the last synchronized production SHA, a
  short content hold or final-delta replay, contribution destination, and recovery
  of edits accepted during a rollback window.
* **Make writes and source identity explicit.** M2 requires argument-array Git
  calls, output-root confinement, and unusual-path controls. M0 includes relevant
  untracked build inputs in its source manifest. No exploit was executed and no
  source file was moved or overwritten during this audit.

## Verification scope and remaining uncertainty

Evidence came from current repository source/configuration, installed Docusaurus
3.10.2 implementation, existing build artifacts, the earlier pinned production
snapshot, bounded file/payload checks, and current official framework/hosting
documentation. Reported observations were checked by the primary reviewer before
being incorporated. Markdown lint, relative-link checks, and preservation checks
validate the edited documents; they do not prove the future migration implementation.

No fresh production-source fetch, full build, Jekyll reference render, live download
request, hosted deployment, cache mutation trial, browser test, or synchronization
pilot was performed in this planning pass. Source/rendering fidelity across the
whole site, strategy cost, and deployment correctness remain implementation work.
This audit supports starting the bounded baseline/validation work and pilot; it
does not establish that migration or launch acceptance has passed.
